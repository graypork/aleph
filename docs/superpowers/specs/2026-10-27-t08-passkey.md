# T08 Passkey Design

## Intent
Extend the existing public introduction page with a clearly separated private area protected only by WebAuthn passkeys. Keep all existing public content available without authentication and never send private note contents to unauthenticated clients.

## Goals
- No password field or password-based fallback.
- Two demo accounts with separate private data for cross-account isolation tests.
- Multiple passkeys per account, human-readable labels, created dates, deletion, and last-passkey state.
- Server-generated one-time challenges for registration and authentication, stored until verification and consumed once.
- Store credential public keys only; private keys remain in authenticators.
- HttpOnly session cookie; logout invalidates the server-side session.
- Direct unauthenticated private-data requests return 401/403.
- Evidence-friendly endpoints and masked submission documentation.

## Non-goals
- Real personal data.
- Password/OAuth recovery.
- Production-grade account enrollment identity proofing.

## Architecture
- Existing Vite page remains the public shell.
- `@simplewebauthn/browser` drives WebAuthn browser prompts.
- Vercel Functions under `api/passkey/` use `@simplewebauthn/server` for option generation and signature verification.
- Existing Upstash Redis environment stores challenges, credentials, sessions, and demo private notes.
- Registration for an account with no credential is open only for initial bootstrap; adding subsequent credentials requires a valid session for that same account.

## Demo accounts
- `miles`: private notes `Bookaive beta checklist`, `PM portfolio next steps`, `Weekly reflection`.
- `sandbox`: private notes `Demo project note`, `Demo application list`, `Demo retrospective`.
All contents are synthetic.

## Security decisions
- Challenge TTL: 5 minutes; verification consumes the challenge before accepting a response so replay fails.
- Session TTL: 8 hours; cookie is `HttpOnly; Secure; SameSite=Lax; Path=/`.
- RP ID derives from request host; expected origin derives from request protocol/host.
- Cross-account reads ignore any client-supplied account selector and derive ownership from the authenticated session.
- Credential deletion requires a session for the credential owner.

## Known limitation
Initial enrollment of an account that has zero credentials is not identity-proofed beyond selecting the demo account. This is retained as the concrete “아직 못 막은 것” item for the assignment report.
